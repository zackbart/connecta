# Render loop before and after #282 — 2026-08-02

## Result

This sample does **not** show that #282 reduced runs-to-correct-view.

| Arm | Correct views | Total `execute_code` runs | Runs to correct view | Correct views whose return mirrored the view |
| --- | ---: | ---: | --- | ---: |
| before #282 | 1 / 3 tasks | 6 | support: 3; sales and reliability: not reached | 1 / 1 |
| after #282 | 2 / 3 tasks | 8 | support: 4; reliability: 3; sales: not reached | 1 / 2 |

Among tasks that reached a correct view, the observed mean was 3.0 runs before
and 3.5 after. That comparison is descriptive, not an estimate: each cell is
one fresh session, failed tasks are not censored into a made-up run count, and
three heterogeneous tasks are far too small a sample for an effect size.

The original claim that moving the batch envelope and adding the return-value
contract would collapse the measured three-run loop toward one or two is
therefore withdrawn. The text remains a more local statement of the contract,
but this measurement does not show that it changed agent behavior.

## Setup

- **Date:** 2026-08-02 (America/New_York).
- **Agent host:** Claude Code 2.1.220, `claude-fable-5`, medium effort. Every
  task and arm started a fresh non-persistent session with only the isolated
  Connecta MCP configured. The host received the complete MCP tool
  descriptions; no additional description truncation was imposed.
- **Before arm:** commit `e1b2261`, release v0.12.0, the parent of #282's
  contract change.
- **After arm:** commit `4ca583e`, release v0.12.1, including #282.
- **Deployment:** the same local authenticated Node deployment in both arms,
  with QuickJS and three in-code API connectors: `operations.queue_snapshot`,
  `sales.pipeline_snapshot`, and `reliability.service_health`. Each tool was
  explicitly read-only and declared an input schema. None declared an output
  schema: **0 / 3 output-schema coverage**.
- **Data:** deterministic nested results. Queue data lived under `report`, sales
  stages under `payload.stages`, and service data under `status`. This made the
  unknown result shape ordinary rather than adversarial: each tool description
  said what it returned without declaring the JSON envelope.
- **Pilot:** an initial prompt that said only “render” produced Markdown and
  never attempted `connecta.ui`. It was excluded. Every counted prompt names
  `connecta.ui` explicitly and is otherwise identical between arms.

A correct view required a successful `execute_code` result carrying `ui: true`
whose HTML contained every requested live value. A return mirrored the view
when the model-visible `result` carried the same records or summary values used
to build the HTML. A run with no accepted view has no view to mirror and is
recorded as `n/a`, not `yes`. Search and other meta-tool calls do not count as
`execute_code` runs.

## What the transcripts say

The batch-envelope mistake from the motivating report did not recur in either
arm: when the agent used batch data, it read `{ address, ok, data }` correctly.
The new location cannot be credited from this sample because the old full
description also contained the envelope and this host did not truncate it.

The guarded-render branch was also not observed. The agent never fetched the
usage skill in any counted session. On the one genuine shape surprise, it used
the returned record to repair a second run, but rendered through `connecta.emit`
rather than `connecta.ui`.

The repeated failure was discovery-shaped: in all six sessions the agent
searched downstream catalogs for a UI or render tool. Three sessions concluded
that `connecta.ui` was absent after those searches, even though it is a guest
function documented on `execute_code`; the other three found it only by
introspecting the guest namespace. #282 did not address that confusion,
and this small record does not justify a new product surface by itself. It does
identify the next claim that would need separate evidence before another
instruction change is proposed.

## Follow-up localization experiment

The six-arm record located a likely ambiguity but did not isolate it. A matched
follow-up used one new task on the current v0.12.1 deployment, three fresh
sessions per arm, and the same host, model, tool definitions, fixture data, and
prompt:

> Using connecta.ui, render compact cards for deterministic records 11 and 12.
> Show each record id, group, and score. Fetch current data from the connected
> tools and render the view.

The intervention added one host instruction before the task:

> `connecta.ui(html)` is a guest function inside `execute_code`. It is not a
> connector address and never appears in `search_tools`. To render, call it
> inside `execute_code` and return the same summary data the HTML displays.

| Arm | Correct views | Runs to correct view | Searched the catalog for UI | Mirrored return |
| --- | ---: | --- | ---: | ---: |
| current instructions | 3 / 3 | 4, 4, 4 | 3 / 3 | 3 / 3 |
| explicit location instruction | 3 / 3 | 1, 1, 1 | 0 / 3 | 3 / 3 |

Every control session first treated UI as a downstream capability, inspected
the guest function, and made an invalid call before rendering. Every
intervention session searched only for the data address, destructured the batch
envelope correctly, passed HTML directly to `connecta.ui`, and returned the two
rendered records in its first `execute_code` run.

This is strong evidence for the *content* of the missing distinction and weak
evidence for its eventual placement. The intervention used the host's appended
system prompt, not Connecta's served MCP `instructions`; an implementation must
repeat the matched check with the candidate text arriving through the product
surface before claiming parity. Six sessions on one task still establish a
reproducible mechanism, not a general effect size.

### Product-surface verification

The #286 implementation moved the tested distinction into Connecta's served MCP
`initialize.instructions`, under a 1,000-character ceiling. The identical task
then ran in three more fresh sessions with no appended host instruction:

| Served surface | Correct views | Runs to correct view | Searched the catalog for UI | Mirrored return |
| --- | ---: | --- | ---: | ---: |
| v0.12.1 current instructions | 3 / 3 | 4, 4, 4 | 3 / 3 | 3 / 3 |
| #286 candidate `initialize.instructions` | 3 / 3 | 1, 1, 1 | 0 / 3 | 3 / 3 |

All three candidate sessions used `search_tools` only to find the data address,
then made one `execute_code` call that batched both records, passed one HTML
string to `connecta.ui`, and returned the same two records. This reproduces the
host-instruction result through the product surface and meets the behavioral
gate. It remains one task with three repetitions, so it validates this concrete
failure and fix rather than making a broad claim about every model or view.
