# Connecta current-version model-run baseline

Date: 2026-07-28 America/New_York

Source: `origin/main` at `b43dd2d85a32953b81af3d827a722d13ee60e5b5`

Server: local loopback sandbox, current source imports, QuickJS code mode

Model driver: one persistent MCP client per task, with the model choosing each
meta-tool and its arguments

The older deployed Connecta instance was not used.

## Scope and measurement

The sandbox used live, read-only public npm and GitHub APIs for realistic
discovery and call work. Deterministic local connectors exercised truncation,
reduction, and a missing static credential without risking external writes.
Every task started a fresh MCP client session.

The driver recorded client-observed MCP latency and exact UTF-8 byte counts for
serialized tool requests and results. It did not have access to the hosting
model's authoritative tokenizer or billed-usage counters, so this pilot does
not claim exact model-token attribution. That remains a harness requirement:
read token usage from the model SDK, rather than inferring it from bytes.

Latency totals below sum MCP operations and exclude model deliberation time.
The initial operation includes MCP connection setup plus `tools/list`.

### Live discovery and fan-out

The model found `@modelcontextprotocol/sdk` version `1.30.0`, its
`modelcontextprotocol/typescript-sdk` repository, the current release, repo
signals, open items, and last-week npm downloads. One `batch_call` ran four
independent public API requests in parallel:

- batch client latency: 257.7 ms;
- Connecta batch duration: 249 ms;
- child connector durations: 174–248 ms;
- observed admission time: 0–4 ms.

The task needed one usage-skill call, one discovery call, two connector-guide
calls, one single call, and one batch call after initialization. Discovery
returned nine matches, including the unrelated `controlled.records` and
`protected.whoami` tools, and cost 7,687 response bytes.

### Code mode

`execute_code` fetched 120 records once, grouped them, computed count/average/
max, sorted them, and returned only the aggregate plus five rows.

Compared with directly fetching and paging the same 7,281-byte source value:

- result-path response bytes fell from 21,215 to 1,268 (94.0% lower);
- result-path meta-tool operations fell from two to one;
- client latency rose from 16.2 ms to 125.5 ms (109.3 ms QuickJS cost).

For reduction work, code mode clearly earns its context cost. The tradeoff is
latency, not correctness or model complexity.

### Truncation and paging

The first call returned a result id and exact total size without an inline
head. Four `get_result` calls reconstructed the 2,338-byte value. UTF-8
boundaries remained valid: a nominal 700-byte page advanced from offset 1,400
to 2,098 rather than splitting a multibyte code point. The final paragraph and
`café, 東京, 🧪` survived intact.

Paging did not stall, but it was easy for the model to over-page. The task
consumed four additional round trips; a task needing only the end could have
jumped directly to a late offset.

### Static credential recovery

`protected.whoami` correctly returned:

```json
{
  "code": "auth_required",
  "retryable": false
}
```

The global usage guide then directed the model to `authorize_connector`.
That tool rejected the connector because static credentials are not downstream
OAuth. `list_connectors({ probe: false })` subsequently exposed the connector
as generic `status: "error"`, not `auth_required`. The bearer-only operator
credential route returned 403 because credential mutation requires Clerk.

After restarting the isolated instance with the disposable credential
pre-seeded, the same call succeeded. Recovery exists, but the model-facing
path dead-ends before it can tell the operator the correct action.

## Ranked weaknesses

1. **Auth recovery conflates OAuth with static credentials.** The guidance says
   every `auth_required` should use `authorize_connector`, while that tool can
   only help OAuth connectors. `list_connectors` also loses the typed
   `auth_required` classification after a real call. This is a meta-tool
   surface problem and should feed back into the documented surface decision.
2. **Structured results are represented twice.** Most results carry both JSON
   text in `content` and the same value in `structuredContent`. In this client,
   a 7,281-byte paged value produced a 20,370-byte tool result. Search and batch
   results showed the same amplification. A real model harness should determine
   whether each supported host forwards both copies into model context.
3. **Broad partial discovery is noisy.** A focused npm/GitHub query returned
   nine of ten sandbox tools, including two unrelated connectors. That created
   a 7,687-byte discovery result for seven useful tools.
4. **Connector guides add serial round trips.** Following the current guidance
   required two extra calls for two short guides (324 response bytes combined).
   The byte cost was small; the round-trip cost and model branching were not.
5. **`fields` is powerful but easy to misuse.** Selecting `0.pull_request`
   returned the entire nested object. Selecting exact leaf paths would have
   avoided several kilobytes. This run classifies it as a model/path-selection
   error, not yet a product defect.

## Positive findings

- `batch_call` parallelized independent downstream work correctly.
- Diagnostics cleanly split catalog, admission, connector, backoff, result
  processing, and total time.
- QuickJS reduction produced a large context saving with one host call.
- UTF-8 paging was correct across a deliberately split multibyte boundary.
- Activity events distinguished `call_tool` from `execute_code` and remained
  payload-free: no arguments, results, generated code, search text, or raw
  error payloads were recorded.
