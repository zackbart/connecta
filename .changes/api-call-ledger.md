Settle API write failures from the whole call's request ledger. A single vendor refusal remains a known failure regardless of its error code; later refusals and handler errors cannot advertise retrying earlier resource dispatches. Preserve GitHub and Cloudflare preflight retry advice and Google Docs composite-create authorization, outcome, and read retry verdicts through recovery wrappers. A write is a known failure only on positive evidence: once a call's outcome is decided, a request still waiting to leave is never sent; no network failure proves a write unsent, a refused connection included, because one fetch can hide several attempts (Node resends after HTTP 421 and an HTTP/2 refused stream, and a dispatcher such as undici's `RetryAgent` can retry further), so a write whose send fails is a non-retryable unknown outcome while a read stays retryable; and a custom `api()` handler's write that fails after the handler started is an unknown outcome, because requests it sends outside `ctx.fetch` are invisible. A direct write outside an invocation that times out or is aborted after it may have left is likewise a non-retryable unknown outcome, through every connector surface (`api()` handlers and `ctx.fetch`, guarded transports, the REST layer, and `remoteMcp().callTool()`), whatever ended it: an SDK or connecta deadline, an HTTP 408, a timeout errno, or the caller's own signal. A timeout keeps its code and `details.code`; the caller's abort keeps its reason as `cause` and its class in `details`, while a read and a served call still receive the caller's abort reason unchanged. A REST `idempotencyKey` that is blank once fetch trims it, or that holds a character fetch cannot send in a header (CR, LF, NUL, another control character, or one past Latin-1), is refused with `invalid_args` before dispatch instead of counting as proof that a retry is safe. Notion's 409 on a write is now a non-retryable `conflict` to reconcile instead of retryable advice; reads keep backing off.
