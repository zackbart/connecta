Settle API write failures from the whole call's request ledger. A single served vendor refusal (an HTTP 4xx other than 408 that the provider does not read as `unavailable` or a timeout) remains a known failure; later refusals and handler errors cannot advertise retrying earlier resource dispatches. Preserve GitHub and Cloudflare preflight retry advice and Google Docs composite-create authorization, outcome, and read retry verdicts through recovery wrappers. A write is a known failure only on positive evidence: once a call's outcome is decided, a request still waiting to leave is never sent; no network failure proves a write unsent, a refused connection included, because one fetch can hide several attempts (Node resends after HTTP 421 and an HTTP/2 refused stream, and a dispatcher such as undici's `RetryAgent` can retry further), so a write whose send fails is a non-retryable unknown outcome while a read stays retryable; and a custom `api()` handler's write that fails after the handler started is an unknown outcome, because requests it sends outside `ctx.fetch` are invisible. A direct write outside an invocation that times out or is aborted after it may have left is likewise a non-retryable unknown outcome, through every connector surface (`api()` handlers and `ctx.fetch`, guarded transports, the REST layer, and `remoteMcp().callTool()`), whatever ended it: an SDK or connecta deadline, an HTTP 408, a timeout errno, or the caller's own signal. A timeout keeps its code and `details.code`; the caller's abort keeps its reason as `cause` and its class in `details`, while a read and a served call still receive the caller's abort reason unchanged. A REST `idempotencyKey` that is blank once fetch trims it, or that holds a character fetch cannot send in a header (CR, LF, NUL, another control character, or one past Latin-1), is refused with `invalid_args` before dispatch instead of counting as proof that a retry is safe. Notion's 409 on a write is now a non-retryable `conflict` to reconcile instead of retryable advice; reads keep backing off. A known failure needs refusal provenance recorded where it was observed: connecta refused the request before it left, or the downstream served a 4xx other than 408. An error code alone never is: a `rate_limited` or `invalid_args` thrown after a 2xx or a 408, a failed output-schema check, or a `remoteMcp()` JSON-RPC error once the `tools/call` was sent (`-32602` included) is a non-retryable unknown outcome on direct and served calls and counts in a program's `writes.unknown`. Operation hints no longer grant retry credit: a direct Google Sheets or Drive write the provider treated as idempotent, and a Vercel content-addressed upload, that fails after it may have left is an unknown outcome; only an idempotency key the vendor honors (Stripe) keeps a direct write's retry advice. A refusing status the provider itself reads as `unavailable` is no refusal either: a keyless Stripe write answered HTTP 424 is a non-retryable unknown outcome, direct, served, and in a program's `writes.unknown`, while a write that sent a genuine idempotency key keeps its retry advice. A served write through a custom connector that throws after it was entered is non-retryable with `writeOutcome: "unknown"` whatever its code, with no "grant the permission, then retry" or "correct the arguments and retry" advice. A write whose downstream answers `input_required` where connecta cannot relay input may already have applied: it is a non-retryable unknown outcome that says to re-read the target before any fresh call, counts in a program's `writes.unknown`, and a direct write's failed relay no longer says to start a new request. Refusal evidence holds only for the whole logical call: a custom connector that composes several calls, or sends on its own around one, never inherits an inner call's known refusal, so a composite whose second Stripe DELETE is refused 429 after its first applied is a non-retryable unknown outcome. A write's MCP `isError` arrives over a 2xx after the handler ran, so it is a non-retryable unknown outcome too, keeping its text; a read's `isError` is unchanged. No text attached to an unknown write says to retry it: an authorization or credential handoff says to re-read the target before any fresh call, and provider advice to wait and retry (rate limits, Notion's 529 overload, Tithe.ly's and Breeze's in-band failures) is dropped from an unknown write's message while reads and known refusals keep it. Google Docs no longer calls repeating an unknown-outcome edit with the same `requiredRevisionId` safe. A custom connector that reassigns its `callTool` during a call can no longer borrow a declared delegator's or a boundary's standing: the invocation and each boundary capture the function identity when it runs, the invocation calls that function with `Reflect.apply` rather than a `call` property a wrapper could replace, and a boundary's or delegator's standing belongs to the object it was built as, so a copy (`{ ...connector }`, `Object.assign`) that shares its function reports an unknown outcome. Advice to send again, including a Google service-account token refusal's and an OAuth flow's "then retry authorization", is kept apart from the message and joins it only when the outcome allows it, so a private argument redacted from the message, or a preflight failure that follows an earlier request in the same call, can no longer keep it on an unknown write. The Google Docs guide no longer offers repeating an unknown edit with the same `requiredRevisionId` as an alternative to re-reading. Concurrent callers that share one Google service-account token refusal now all keep its advice. Stripe's write tool now says an idempotency key makes only a POST safe to retry, since a DELETE sends none. Advice to reuse an idempotency key ("cannot repeat the write", "reusing it ... retries this write without repeating it") now appears only when the call entered exactly one connector boundary and sent exactly one write, carrying that key; GET and HEAD reads beside it do not count. A custom connector that composes a keyed Stripe create with another write, or two keyed creates, or wraps a single Stripe call, still reports the key in its message and `uncertainCall.recovery`, but only as a diagnostic, never with advice to reuse it.
