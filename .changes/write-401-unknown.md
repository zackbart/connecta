A write the downstream answered with HTTP 401 now has an unknown outcome by default in maintained providers and `api()` connectors, since a server may act on a request before it rejects the credential. It keeps its `auth_required` (or `downstream_oauth_required`) code, `reconciliationRequired: true`, and the `authorize_connector` handoff, whose instructions say to authorize and then re-read the target before any fresh call; it gains `writeOutcome: "unknown"`, a message saying the write was sent before the vendor rejected its credential, and no retry advice, key-reuse advice or wait. That holds whatever the call met after the 401 (a body past the response ceiling, a later failure in the same call, a 401 on a composite write's later request, a custom `api()` handler, a 401 answered inside another `api()` or `remoteMcp()` connector the call reached, directly, through a custom connector or from a program, or the call's deadline or the caller's cancellation, which no longer report `write_outcome_unknown` with key-reuse advice) and whatever idempotency key the write carried. Such a call never succeeds: a handler that caught the 401 and returned, or a result that could not be processed, still ends in that verdict, and programs count the write in `writes.unknown`. Before this, Breeze, Cloudflare, GitHub, Mixpanel, Notion, Overflow, Planning Center, Tithe.ly and Vercel reported such a write as a known refusal. A provider keeps that refusal only with reviewed vendor documentation that the vendor authenticates a request before acting on it: Stripe's API-key connector does, for an API v1 answer carrying Stripe's `Request-Id`, since Stripe documents an invalid API key as an error that occurs before execution begins, so its write 401s are unchanged. A write whose credential renewal fails after a 401, for any reason, keeps the 401's authorization code and handoff with an unknown outcome; before, a renewal that failed without an authorization verdict (an operator disconnect racing an `api()` OAuth refresh, an Infisical login outage, a direct `remoteMcp()` write whose caller left during the refresh) became `connector_call_failed`. A renewal that succeeds still leaves a non-retryable `connector_call_failed` with an unknown outcome, even if the handler catches the failure and returns, and no write is ever sent again after a 401. A renewal succeeds only when it yields a different credential than the one the write sent: a refresh or login that hands back the rejected token (remote MCP's OAuth refresh included), or an Infisical recovery already spent earlier in the same request, renews nothing, and the write keeps its handoff. A call whose renewed write shares it with another write stays unknown, never retryable, with no wait or key-reuse advice. A direct guarded transport settles successful mapper returns too. A caught read 401 (positive operation/tool classification plus a recorded GET or HEAD is required; method-override headers always count as writes), or a declared refusal followed by a successful write, does not block success. Reads answered 401 are unchanged.

A guarded transport that delegates through `ctx.fetch` now shares its bound request entry instead of recording a duplicate. A declared refusal followed by a successful write therefore keeps its successful result.
