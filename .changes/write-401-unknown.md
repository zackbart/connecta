A write the downstream answered with HTTP 401 now has an unknown outcome by default in maintained providers and `api()` connectors, since a server may act on a request before it rejects the credential. It keeps its `auth_required` (or `downstream_oauth_required`) code, `reconciliationRequired: true`, and the `authorize_connector` handoff, whose instructions say to authorize and then re-read the target before any fresh call; it gains `writeOutcome: "unknown"`, a message saying the write was sent before the vendor rejected its credential, and no retry advice, key-reuse advice or wait. That holds whatever the call met after the 401 (a body past the response ceiling, a later failure in the same call, a 401 on a composite write's later request, a custom `api()` handler) and whatever idempotency key the write carried. Programs count it in `writes.unknown`, caught or not. Before this, Breeze, Cloudflare, GitHub, Mixpanel, Notion, Overflow, Planning Center, Tithe.ly and Vercel reported such a write as a known refusal. A provider keeps that refusal only with reviewed vendor documentation that the vendor authenticates a request before acting on it: Stripe's API-key connector does, for an API v1 answer carrying Stripe's `Request-Id`, since Stripe documents an invalid API key as an error that occurs before execution begins, so its write 401s are unchanged. A write whose credential renewal fails after a 401, for any reason, keeps the 401's authorization code and handoff with an unknown outcome; before, a renewal that failed without an authorization verdict (an operator disconnect racing an `api()` OAuth refresh, an Infisical login outage, a direct `remoteMcp()` write whose caller left during the refresh) became `connector_call_failed`. A renewal that succeeds still leaves a non-retryable `connector_call_failed` with an unknown outcome, and no write is ever sent again after a 401. Reads answered 401 are unchanged.
