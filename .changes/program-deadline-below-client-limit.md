Answer before MCP clients give up, so an agent gets a typed `timeout` or `write_outcome_unknown` with `hostCalls` and `writes` rather than a transport `The operation timed out`. Claude Code and Codex both give one request 60 s by default. `execute.watchdogMs` now defaults to 55 s (was 120 s), counts from the request's arrival so queueing spends it, and caps direct `call_tool`/`call_destructive_tool` deadlines, including an explicit `timeoutMs` or `calls.defaultTimeoutMs`. `workerExecutor()` now defaults to a 50 s `timeout` (was 60 s) and a 40 s queue deadline (was 60 s); `quickJsExecutor()` keeps 30 s. A run cut short by the ceiling rather than wedged fails as a `timeout` at stage `response ceiling`, retryable unless a write in it landed. Any program error is now non-retryable and drops `retryAfterMs` once a write in the run has landed, because running the program again would repeat it. A run or direct call with no time left is refused unsent, and a call whose time runs out during catalog resolution, admission or auth is refused unsent by a check immediately before dispatch. On Node, the ceiling also counts the request's upload. Storage after a run stops waiting 2 s past the ceiling at most, so a stalled store costs an oversized return its paging, not its answer.

Migration: if your clients allow longer requests (`MCP_TOOL_TIMEOUT`, a server's `timeout`, `tool_timeout_sec`) and your programs or direct calls need the time, set `execute.watchdogMs` a margin below that limit, then raise `workerExecutor({ timeout })` or `quickJsExecutor({ timeoutMs })` below it. Construction warns when an executor's deadline is not below `execute.watchdogMs`.
